# TOM — designing a screen

**Nothing the user can see is written in Dart before it exists in Penpot and the maintainer has approved it there.** Not a screen, not a panel, not a button. The design is the gate, the approval is how it is passed, the exported board in the repository is the record of it, and a rendered screenshot beside that board is the proof the app kept its word.

The whole point is fidelity: what ships has to look like what was designed. Designing first is half of it, and checking afterwards is the other half — a board drawn and never compared to the running app buys nothing.

That is stricter than it was. The old rule asked for a mock in the same pull request, which is how the rendered diff shipped ahead of its own drawing and how the compare surface was designed in code. Deciding what something looks like while typing it is how a product ends up with four kinds of button.

## The two artifacts

| | Penpot file | Exported board |
|---|---|---|
| Answers | what it looks like | what it looked like at commit X |
| Lives in | Penpot — `docs/design/TOM.penpot` is only a local backup, gitignored | `docs/design/screens/desktop/<page>/` |
| Format | boards, on a `Screens: <subject>` page | `<screen>-light.svg`, `<screen>-dark.svg` |
| Required | **always, and approved by the maintainer before any code** | **always, before the merge** |

`docs/design/` is a top-level chapter beside `product/` and `technical/`, one folder per subject: `brand/`, `components/`, `foundations/`, `screens/`, `site/`, `visual-language/` and `tools/`. Each holds its own `README.md`, its exports, and nothing else.

The Penpot file is the source. The export is what a reader, a reviewer and a diff can see without an account — **a board nobody approved does not count as designed, and a board nobody exported does not merge.**

- **Approved in Penpot before code, exported before merge.** The two used to be one step ("exported in the same commit"), and the export is too slow to be one.
- **The export runs only when the maintainer asks for it** — it locks the file and the session for as long as it takes, so it is the end of the work, never a step of it. Work that draws boards ends at "drawn and approved in Penpot".
- **An export is never edited by hand.** A wrong export is a board to change in Penpot and export again.

There used to be a third: a set of Excalidraw wireframes, generated by a kit in this repository. They answered where things are, back when there was no palette to apply. Every desktop screen they held now has a board, so they were removed rather than kept as a second drawing to update twice and disagree with once.

## The gate, in order

1. **Design the board in Penpot**, light and dark, at 1440×900, on the `Screens: <subject>` page of its flow — the cover's contents is the list of pages. A new flow is a new page. **A page is one flow, and it splits when two flows start sharing it, or when it passes eight screens** — a card that scrolls for ever is no longer read at once.
2. **Build every control from the library.** A control that is not there yet becomes a master on `Components - Master`, with its variants, before the screen uses it.
3. **Ask the page what it drew by hand**, and go on only once the answer is empty — the query is under *Say it, then check it*. A control the screen drew instead of instancing looks right until the master changes and it does not.
4. **The maintainer approves the board in Penpot.** Code starts here and not before; a board that is drawn and not approved is a proposal.
5. **Write the widget**, against what is on the board.
6. **Render it and compare.** The point of all of this is that the app looks like the design, and the only way to know is to look at both — at the board's own size, with the tools under *Measuring the app against a board*. A screen nobody compared is a screen that has already drifted.
7. **Export both themes** into `docs/design/screens/desktop/<page>/` and run `embed_fonts.py` over them — before the merge, when the maintainer asks for the export.
8. **Link the screen** from the feature's `doc.md`, under `## Mocks` — once the file it points at exists.

A change to a shipped screen runs the same steps. The board is edited and approved before the code changes, and exported again before the change merges — a board that no longer matches the app is worse than no board, because it carries the appearance of authority.

## Every control is a component

"Every button" is not a figure of speech. A control that appears on a screen exists as a **component master on the `Components - Master` page**, with its states as variants, and the screen places an instance of it. Which masters exist, with their sizes and states, is [`controls.md`](../../../docs/design/components/controls.md) — one row each, and the roster is not repeated here so the two cannot drift.

The library's pages divide the work and none of them do each other's: `Components - Master` holds the masters of the controls, `Components - Shell` the masters of the window's own regions, `Components - Catalogue` the specimens one row per control, and `Foundations` the palette and the type scale with no component on it at all. Keeping them apart is what lets the library be read without the specimens in the way of it.

Two things follow from that, and both have bitten already:

- **A new control is a library change first.** Adding a master and its variants is a separate, smaller decision than the screen that needed it, and reviewing it separately is what keeps the set coherent.
- **An instance is never detached to restyle it.** If a screen needs a control to look different, the difference is a variant of the master, or the master is wrong.

### Say it, then check it

This rule was written in two places and broken anyway: the commit message box,
the new-branch name field and the search box were each drawn by hand, and the
master the search box did point at had been deleted out from under it, leaving
instances nobody could update. Nothing caught it because nothing looked. So the
rule ships with the query that enforces it, and the query runs before an
export:

```js
// A control the screen drew instead of instancing, and an instance whose
// master no longer exists. Both read as ordinary shapes until asked.
const ids = new Set(penpot.library.local.components.map(c => c.id));
const stray = [], ghost = [];
for (const board of card.children.filter(c => c.type === 'board')) {
  for (const s of penpotUtils.findShapes(x => x.type === 'board' || x.type === 'rectangle', board)) {
    const c = typeof s.component === 'function' ? s.component() : null;
    if (!c) { if (/field|button|chip|toggle|mark/i.test(s.name)) stray.push(s.name); }
    else if (!ids.has(c.id) && !c.isVariant?.()) ghost.push(`${s.name} → ${c.name}`);
  }
}
```

A name match is a heuristic, not a proof — it catches what a screen *calls* a
control. The point is that a list comes back and somebody reads it, which is
more than the rule alone ever did.

**Zero instances is not evidence that a control is unused**, and reading it that
way cost two variants of `Text field`, destroyed before anybody noticed. The
count under-reports for exactly the reason this section exists: a control the
screens draw by hand instances nothing, so the master it should have used looks
abandoned. The catalogue's `USED IN` line is the statement of intent, and it
outranks the count. Check it before removing anything.

Two Penpot facts the code has to encode: `library.components` lists one entry per variant *set*, and the rest are reached through `variants.variantComponents()`; and the plugin draws only on the **active page**, so anything touching the library switches page and switches back.

### Never move a master between pages

The masters of the controls live on `Components - Master`, in a board called `Masters`, the masters of the window's regions on `Components - Shell`, and **they stay where they are**. Penpot keeps every component's original as a real shape, so the board cannot be deleted, and it cannot travel either:

- **Duplicating a page that holds main instances duplicates the components.** It did, twice, and both times it was the ones with variants.
- **Cut-and-paste rebuilds a variant set** that crosses a page. A plain component is different: the shell masters went to `Components - Shell` by ⌘X / ⌘V in the Penpot app and kept their component *and* main-instance ids, so every screen stayed linked. A plain master can be moved by hand in the app, a variant set cannot — count the library either way.
- **The plugin cannot move a shape between pages at all** — `appendChild` answers `Cannot modify a page that is not currently active`, and a reference taken on one page is invalid on another.

What *is* safe to move is an ordinary instance, which is how the catalogue crossed pages without losing a component. **Before and after any page surgery, count the library** (`penpot.library.local.components.length`): a count that jumped is the whole of the damage, and undo is the only clean repair.

### Making a component, and a variant set

`library.createComponent(shapes)` and `penpot.createVariantFromComponents(shapes)` both take **shapes**, never `LibraryComponent`. Passing components fails with `Code: :shapes`; pass each one's `mainInstance()` instead. The shapes must be on the active page.

A **slash in the name becomes a path**: creating `Panel toggle / Left Open` yields a component called `Left Open` under path `TOM / Panel toggle`. Name the parts plainly and let the variant set carry the family name. The grouped property arrives as `Property 1`, not as the word you had in mind, so read `variantProps` before writing code that switches on it.

**Grouping lowers the count**: loose components become one set, so the library's count drops by one for each component the set absorbed. That drop is the success signal, and the mirror image of the duplication failure above — predict the number before the call, and stop and undo in the tab if it reads anything else.

### A master carries no product words

A master's labels are `One`, `Two`, `Three`, never `Source`, `Split`, `Preview`. Text is a property, so the screen that places the instance writes the real words; a master that ships a product's vocabulary is a master that only fits one screen.

The same goes for the name: `Switch` is the on/off control, so a two-segment control is **not** a `Switch`. Where a family cannot be one variant set, put the distinction in the name — `Segmented · 2` and `Segmented · 3` — so the two sort together and neither collides with something else.

### A component must fit the use, not the other way round

`Segmented` ships three segments with fixed labels. The two-segment switches could not use it, because dropping a segment is a structural change to a copy, which Penpot forbids. They got `Switch two` instead. **When an existing component nearly fits, check whether the difference is a property (colour, size, text, flex) or a child — a property is an override and a child is a new component.**

### Never restructure a copy

`Cannot change the structure of a component copy` is Penpot refusing to add or remove a copy's children, and it is right to. So **editing a master means editing its children, never replacing them** — replace them and the copies keep the old structure and can no longer be repaired in place. When that has already happened, delete the stale instances and insert fresh ones of the right variant, then re-apply the theme colours, which are overrides and do survive.

Colour, size and flex *are* overridable on a copy. A control that looks wrong in one theme is usually an override that was never set, and a label sitting outside its control is usually a flex `justifyContent` with padding, not a bad `x`.

**A board carries no milestone chip.** `M0`, `M1`, `M2` are a wireframe's way of saying *this part arrives later*, and a board says what the app looks like — a chip on it is a note to the team pretending to be part of the product. The roadmap is where a milestone lives.

## The file, page by page

The file reads front to back like a document, and **a new project starts by creating these pages empty, in this order**, before a single screen is drawn. Nothing here is this product's: swap the name and the subjects.

| # | Page | Holds |
|---|---|---|
| 00 | `Cover` | the front: name, one line of what it is, the logo, a drawing of the app, three facts (`Milestone` · `Date` · `Pages`) and the **contents** — one numbered row per page |
| 01 | `Why <product>` | why it exists, for somebody who opens the file cold: the lead, today's options and what each lacks, the bet, the principles as boxes |
| 02 | `Brand` | the lockup on each tile, the icon at 16 · 32 · 64 · 128, the wordmark |
| 03 | `Components - Catalogue` | every control as a specimen, one row each, with what it is for and `USED IN` — both themes |
| 04 | `Components - Master` | the main instances, in one board called `Masters`; nothing else |
| 05 | `Components - Shell` | the masters of the window's own regions (bars, columns), which every screen instances |
| 06 | `Foundations` | colour roles and the type scale, both themes, no component |
| 07… | `Screens: <subject>` | one page per flow, grouped by product area (`Screens: Git - Commit`) |
| last | `Site`, then `Prototypes` | the landing page; and what was tried — kept in the file, never exported |

- **A page's name is `NN · <name>`**, two digits, and the number is its place in the file. A page added in the middle renumbers the ones after it — in the page names, in every card's page number and in the cover's contents, in one pass.
- **The plugin cannot reorder pages**: it creates one at the end, and somebody drags it. The names carry the order so the dragging has something to follow.
- **Docs cite a page by its name, never its number**, because the number moves.
- **Cover and `Why` are 3732 wide like a card** but set larger — margins of 152, a 120pt title, 32–48pt text — because they are read from far away, as a slide is.

## Every page is a card

A page is one **card**: a single board holding everything on the page, with the same frame every time, so the file reads as one document rather than a pile of drawings. The card is named for its subject (`Workspace · tree`) and filled `#faf9f6`, whatever theme the boards on it wear.

| Element | Where | Set in |
|---|---|---|
| `title`, the subject | 64, 64 | 56pt, weight 600, `#26251f` |
| `note`, one sentence saying what the page is | 64, 148 | 28pt, regular, `#8b877d` |
| `page number` — `<Section> · NN / <total>` | top right, its right edge 64 from the card's, y 81 | 28pt, weight 600, `#8b877d` |
| `shot title / <row>` | 64, row `y` − 48 | 26pt, weight 600 |
| dark board | 64, row `y` — the first row at 286 | 1440 wide |
| light board | 1552, row `y` | 1440 wide |
| `feat / <row> / …`, the notes | 3048, row `y` | below |
| next row | previous board's bottom + 136 | |

`<Section>` is `Library` on the component and foundation pages and `Screens` on the rest. The card is 3732 wide **only when the page has notes**; without them it ends where its content ends plus the same 64 it starts with (3056 for two boards, 1576 for one). It ends 136 under its last board. The light board carries the screens' own outer border, `#26251f` at 1pt.

### The notes beside a row

Every row carries a column of notes at x 3048, 620 wide, and **every row's first note is `Why this screen`** — a screen nobody can say the reason for is a screen to delete.

| Shape | Name | Set in |
|---|---|---|
| the row's name | `feat / <row> / name` | 34pt, weight 600, at row `y` |
| a note's title | `feat / <row> / <title>` | 20pt, weight 600, 58 under the name, then 11 under the body before it |
| a note's body, one or two sentences | `feat / <row> / <title> body` | 16pt, regular, `#57544c`, 620 wide, 30 under its title |

- **Three to six notes a row**: why the screen exists, then one per rule the drawing cannot say by itself — what a control does, what is deliberately absent, what was decided against.
- **A note states a rule, never describes the picture.** `Collapse all keeps what is on screen` is a note; `A menu with four rows` is not.
- **The names are the index.** `shot title / <row>`, `<row> · Dark`, `<row> · Light` and `feat / <row> / …` are how a script finds everything that belongs to a row, moves it and removes it. A shape named anything else is left behind.
- **A title's box is as wide as its words** and a body's as tall as its lines; a box left at the template's size wraps one note over the next.

### The first screen whole, then only what varies

The maintainer's rule (2026-10-10), after `Pull request row — states`:

- **The first row of a page is always a whole window**, 1440×900, both themes. It is what says where the thing lives and what surrounds it.
- **After it, when what differs between two screens comes down to one component or one part of the window, the whole window is not drawn again**: the row draws that piece alone, in every state side by side: one board per theme, the states in a line, each under a short label (`Available`, `Open`, `No remote`). Not a fresh window per state.
- **It is one component when the rest of the window would be identical** — a dialog's words, a popover's choice, a band's sentence, a column's foot, a panel's rows, a button waiting. If the state moves something elsewhere (a column closes, the document changes, a second region answers), it is a screen and gets its window.
- **The piece is cut where it is whole**: the column, the popover, the dialog, the panel — never half of one. It sits on the window's own surface, at its real size, so a number measured on it is the app's number.
- **Each state keeps its note.** `Why this screen` becomes why the states exist; one note per state that needs saying.
- **A states board is as wide as a window, and its pieces sit in the middle.** 1440 across like every screen above it, as tall as the pieces need, the row of states centred on it. The card then reads as one column of equal boards, dark at 64 and light at 1552, whatever a row holds.
- **A states board is only as tall as its pieces, and the next row comes up to it.** 136 between one row's boards and the next, whatever the heights. Notes that run longer than a short board hang into that gap; the board is never stretched to hold them, and the row below moves down only when the notes would otherwise reach it.
- **Both themes, every state.** The states board is drawn twice, dark and light, with the same states in the same places — the maintainer's correction (2026-10-10) to a first attempt that drew light only by sample. A piece is small enough that drawing it twice costs little, and a state nobody drew in light is a state nobody checked in light.
- **A states board says where its piece sits in the window** — `x, y · w × h`, in its notes under *Where it sits* — taken from the whole window above it. That rectangle is what makes a piece measurable: the app's frame is cropped to it and compared with the state (`compare.py` crops any rectangle), and a test that renders the widget alone at that size is compared with the same piece. Both, so no state needs a window of its own to be held to the pixel.
- **The export follows the board**: a states board is one file per theme, `<component>-states-{light,dark}.svg`, and a doc's `## Mocks` names the state inside it.
- **The `Prototypes` page stays in the file and is never exported.** It is the road to the product, kept where it was drawn; the repository holds only what the product is (the maintainer's call, 2026-10-10).

A page built this way reads as *here is the screen, here is everything this part of it can say* — and a change to the shell stops costing a sweep over twelve identical windows.

**A label belongs above the board it names, not inside it.** And a board never repeats the card's title: the card is the frame and carries the words, the board is the content.

**Text boxes go stale.** A title that renders at half its size has a collapsed bounding box, not a wrong font — check `width`/`height` against a good card before touching the font. Resizing does not recompute it and neither does round-tripping `growType`; delete the text and create it again. A freshly created text measures `1x1` until the next call, so read it back in a separate one.

## Exporting

**The export runs when the maintainer asks for it, and before the merge** — never while building, and never as the check that a write landed (see *Traps*).

Every page produces one kind of file, into `docs/design/screens/desktop/<page>/`:

| File | What it is | How |
|---|---|---|
| `<screen>-light.svg`, `<screen>-dark.svg` | a whole window alone, both themes | `board.export({type: 'svg'})` then `embed_fonts.py` |
| `<component>-states-light.svg`, `<component>-states-dark.svg` | a states board, both themes | the same |

- **The card is not exported.** A page's PDF used to carry the title and the notes; nothing in the build reads it, so the notes live in Penpot only and a PDF still on disk is stale by definition.
- **The `Prototypes` page is not exported.**
- **The page's name decides the folder** — re-read it before exporting, because a rename does not always hold.

**SVG only for screens, never PNG.** The SVG keeps the text searchable and the diff readable, and once the fonts are in it is pixel-faithful. A PNG buys nothing and turns every review into a binary blob.

**`embed_fonts.py` is not optional.** Penpot's SVG export points its `@font-face` rules at Penpot's own font proxy, which nothing offline can reach, GitHub included. Without the script the text falls back to whatever font is at hand and every monospaced run reflows, which is a file that looks finished and is wrong.

```bash
python3 docs/design/tools/embed_fonts.py docs/design/screens/desktop/*/*.svg
```

**Do not judge the result with `rsvg-convert`.** It does not match a font family written `&quot;IBM Plex Mono&quot;` in an inline style against an `@font-face` that quotes it differently, so it drops every mono face and blames the file. Render with headless Chrome, which is what VS Code and GitHub use:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --force-device-scale-factor=2 --window-size=1444,1250 --screenshot=out.png "file://$PWD/<screen>.svg"
```

**An agent exports without reading a byte of it.** A board is 130–300KB of SVG and fifty will not fit through a conversation, so the plugin returns `{filename: base64}`, the harness writes that oversized answer to a file because it cannot be returned, and `tools/decode_exports.py` decodes it straight into place. The bytes go browser to disk and are never read. Return **only** the file map from the plugin: one stray diagnostic key and the decoder chokes on it. Do not try to post the bytes to a local server instead — the page is served over https, so the browser blocks it, and the sandbox blocks the server.

**Batch four to six boards per call.** Beyond that the plugin call passes 120 seconds and is moved to the background, where its answer is lost, and Penpot's own `/api/export` starts returning `:timeout`. A page of eight is two calls, split by theme.

The file name is the screen's name in kebab-case plus the theme: `branch-switcher-light.svg`. One screen is two files, always both.

## Look at it before committing

Render and actually view both themes. A board with a clipped label, a control that fell outside its panel or a dark variant nobody checked is invisible in an SVG diff and obvious on screen. The `export_shape` tool answers this directly.

**The card is not the screen.** Each page holds the screens inside a card that carries the title, the note and a column of what the screen is for. That framing is documentation and lives only in Penpot — an export is the board alone.

## Measuring the app against a board

**The app is held to the board by measuring, never by eye** — and against the export, never by opening Penpot to check. The kit is in [`docs/design/tools/`](../../../docs/design/tools), pure Python because the machine has no Pillow:

| Tool | Answers |
|---|---|
| `render.py` | an SVG board as a PNG at the board's own size, through headless Chrome — both sides measured with one ruler |
| `pixels.py` | the colour runs along a row or a column; a shape's edge traced row by row |
| `bbox.py` | where the ink actually is inside a rectangle |
| `compare.py` | board, app and their difference in one PNG, cropped to any rectangle |

- **A comparison is only real at the board's own size.** `dart run tool/cli.dart e2e "<the scenario's name>" --board` runs the real app at 1440×900; against any other window one side is scaled and every number taken off the image is a number about the scaling.
- **The render is the judge, not the markup.** Reading an SVG alone missed a `text-decoration: line-through`, a clear disc, a four-point gap and a mid-word cut. Put board and app side by side in one PNG.
- **A zoomed screenshot lies about a radius.** Read the pixels (`pixels.py`) before believing a corner is wrong.
- **Read a shape's pixels at its mid-height, never at its top row** — a rounded corner makes a control read narrower than it is.
- **A board draws a library component with its abstract labels** — `One`, `Two`, `Item name` — so grepping an export for the product's words finds nothing. Measure the shape, not the text.
- **A column's width is never the finding.** The columns are dragged, and boards draw the same column at different widths.
- **A states board is compared twice**: the app's frame cropped to the rectangle its notes give under *Where it sits*, and the widget rendered alone at that size ([`tom-testing`](../tom-testing/SKILL.md)).
- **Where the app and a board disagree, or two boards do, the finding goes in [`screens/divergences.md`](../../../docs/design/screens/divergences.md)** with both numbers — which of the two moves is the maintainer's call.

## Traps

Every one of these cost a session in the Penpot file. They are about the plugin and the file; the code's own traps are in [`AGENTS.md`](../../../AGENTS.md) and the test side's in [`tom-testing`](../tom-testing/SKILL.md).

**The facts about the library's API — variant sets, variant containers, what a copy may override, what `component()` answers — live in [`components/penpot-traps.md`](../../../docs/design/components/penpot-traps.md) and are not repeated here.** Read it before touching a master. What follows is the procedure around them: the tab, the pages, whether a write landed, sweeps and the export.

### The plugin and its tab

- **The Penpot tab suspends after a few minutes without focus**, and the plugin then answers nothing: a call that hangs or fails on the heartbeat is a sleeping tab, not a heavy script. Focus the tab.
- **A call that failed has usually landed.** Check the document before repeating the work, or it is done twice.
- **The plugin connects to whichever file the tab has open.** Check `penpot.currentFile.name` before the first write of a session, and again after any pause — somebody else may have worked in the file, and the page can change under a read.
- **A reconnected plugin can stop sending**: the tab shows every write and the server has none. Probe it — create a shape and `export_shape` its **new id**, which has no cached render. If the probe is missing, reload the tab and redo the work.
- **Keep every change scripted and idempotent**, for exactly that: a script that reads its own output back makes a second run a no-op and a lost run cheap.
- **`storage` is emptied when the plugin reconnects.** Helpers kept there are re-created before they are trusted.
- **One board, or one pair, per call.** A sweep that mutates many boards in one call is hundreds of changes; it freezes the tab and the queue is dropped when it resumes — with the client still showing the work.
- **`revn` on `penpot.currentFile` is not a write indicator.** It stands still through changes that persist.
- **A call past two minutes is moved to the background and its answer is lost** — which is what bounds a batch of exports too.

### Pages and `openPage`

- **`openPage` takes effect on the next call, sometimes the one after, and writes do not wait for it.** Every call that writes checks `penpot.currentPage.name` first — a rename and a new shape have both landed on the previous page.
- **A write followed by `openPage` in the same call is lost.** The client keeps the new value and the server the old one, and a retry does nothing because the model already reads as correct. Never switch pages in a call that wrote.
- **To re-send a value the model already holds**: set an obviously wrong one, `await` an export to flush it, then set the right one — assigning a value a shape already holds writes nothing ([`penpot-traps.md`](../../../docs/design/components/penpot-traps.md)).
- **The plugin cannot move a shape between pages, duplicate a page or reorder pages.** `penpot.createPage()` exists and creates at the end; somebody drags the page into place.
- **`penpot.root.children` is not the file's pages** — `penpot.currentFile.pages` is.
- **A page rename does not always persist.** Re-read the name before trusting it.
- **Duplicating a page in the app keeps every shape's id**, so the copy collides with the original, a reload does not re-id it, and `export_shape` renders the *original* board. Cloning the card inside the page re-ids everything it holds; compare the two id sets before trusting a duplicated page.
- **Duplicating a page that holds main instances duplicates the components** — *Never move a master between pages*, above.

### Writes and renders

- **The model says what the client holds; a render says what the server holds, late.** A model that reads right does not prove the write reached the server, and a render that looks old does not prove it was lost.
- **The server's render lags a write by seconds to minutes**, and `export_shape` serves a cached render per shape id on top of that. Sweep every page first and export last.
- **A render that still disagrees with its model after that is a real defect**, and for a text it is the face: `font.applyToText` again fixes it, waiting does not.
- **`shape.export()` is the check that a write reached the server** — taken at the end of a page's work, not straight after each write.
- **`setParentXY` is relative to the current parent.** A shape positioned before `appendChild` lands at those coordinates absolutely and then leaves the board — append, then position.
- **Two shape proxies are never `===`.** A filter `s !== other` keeps everything; compare by id or by name.
- **`fills` is a proxy** — `Array.from` it before reading; **`isVariantContainer` is a function**.
- **A created or cloned text reports a stale size until the next call** — `1×1`, or the template's height. Read it back in a separate call before laying anything out by it.

### Components and copies

- **A copy freezes its master's text at the moment it is made.** Editing the master afterwards does not reach it, writing to the copy's own label does not either, and cloning the copy carries the frozen word along. Only `component.instance()` picks the current word up — replace the copy.
- **A `find` by name over `library.components` edits one variant of a set and leaves the rest untouched** — the list holds one entry per set ([`penpot-traps.md`](../../../docs/design/components/penpot-traps.md)).
- **`remove()` inside a component copy hides rather than removes.** The shape reads `hidden: true` and the board renders as if it were gone — until something clones it. Check `hidden` before concluding a shape was deleted.
- **A copy that overrides a child's position keeps that child when the master deletes it.** A control removed from a master is then drawn twice on every such copy; sweep the copies after the master.
- **A copy keeps the structure it was made with.** Rebuilding a master's children leaves every copy on the old ones — which is why a rule that lives in nested copies (an unavailable toolbar button inside `Document`) is a colour override on the screens and a variant in the library, not a swap.
- **On `Components - Master` every master is a loose board.** An orphan-hunter that defines an orphan as "a board that is neither a card nor a screen" deletes the library.

### Text and fonts

- **`fontStyle = 'italic'` is accepted, reads back as `italic`, and renders roman.** The face carries the cut: only `font.applyToText(text, variant)` reaches it, and the same is true of any weight outside the default.
- **A copy's text can lose its font variant and draw nothing while the model still holds the words** — the account disc's initials did. Re-apply the face.
- **IBM Plex Sans carries `↑`, `↓` and `✓` only in its regular cut.** At weight 500 or 600 they export as nothing, silently.
- **A symbol that is not a letter comes from the icon set, never from text** — `Icon[check]` is a path and has no cut to miss.
- **A text box goes stale** — *Every page is a card*, above: delete the text and create it again.

### Sweeps

- **A destructive sweep is written read-only first, run, and read — then given `apply`.**
- **⌘Z in the tab is the recovery path**, so stop touching the file the moment something looks wrong; every further write buries the undo.
- **A shape's name is not an index.** The right column's divider is `git / rule` on some pages and `history / rule` on others, so a sweep that matches by name skips boards and reports success. Match on geometry, and read the result back.
- **"The right column" by x alone is wrong on a board whose column is closed** — at that x it finds the preview's table cells. Ask for a `shell / git box` before believing there is a column.
- **A board whose explorer is closed has no `document box` to measure**: the shape by that name is the full-bleed container at `-8`, and the content runs `0..1440`.
- **A note named outside `feat / <row> / …` is left behind by every restack** — *The notes beside a row*, above.

### The export

- **Penpot sometimes sends an SVG without its style block**, and `embed_fonts.py` then reports it as already embedded. After every export: `grep -L "data:font" docs/design/screens/desktop/*/*.svg`, and export again what it lists.
- **A loose shape parented to `Root Frame` instead of the card** is invisible in a board's own SVG and breaks an export of the card (`locator.waitFor: Timeout 10000ms`) — and an ordinary timeout that a second attempt clears looks identical. Sweep for orphans, retry once, and only then suspect the service.
- **`rsvg-convert` is not the judge** — *Exporting*, above.

## Where the reasoning goes

Colour roles are decided in [visual-language](../../../docs/design/visual-language/README.md), the controls in [components](../../../docs/design/components/README.md), the identity in [brand](../../../docs/design/brand/README.md). None of it is annotated onto the board: a picture crowded with explanation stops being a design and starts being a diagram nobody updates.
