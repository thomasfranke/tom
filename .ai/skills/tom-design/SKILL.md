# TOM — designing a screen

**Nothing the user can see is written in Dart before it exists in Penpot.** Not a screen, not a panel, not a button. The design is the gate, the exported board in the repository is the proof it was passed, and a rendered screenshot beside that board is the proof the app kept its word.

The whole point is fidelity: what ships has to look like what was designed. Designing first is half of it, and checking afterwards is the other half — a board drawn and never compared to the running app buys nothing.

That is stricter than it was. The old rule asked for a mock in the same pull request, which is how the rendered diff shipped ahead of its own drawing and how the compare surface was designed in code. Deciding what something looks like while typing it is how a product ends up with four kinds of button.

## The two artifacts

| | Penpot file | Exported board |
|---|---|---|
| Answers | what it looks like | what it looked like at commit X |
| Lives in | `docs/design/TOM.penpot` | `docs/design/screens/desktop/<page>/` |
| Format | boards, on a `Screens: <subject>` page | `<screen>-light.svg`, `<screen>-dark.svg` |
| Required | **always** | **always, in the same commit** |

`docs/design/` is a top-level chapter beside `product/` and `technical/`, one folder per subject: `brand/`, `components/`, `foundations/`, `screens/`, `site/`, `visual-language/` and `tools/`. Each holds its own `README.md`, its exports, and nothing else.

The Penpot file is the source. The export is what a reader, a reviewer and a diff can see without an account — **a board nobody exported does not count as designed.**

There used to be a third: a set of Excalidraw wireframes, generated by a kit in this repository. They answered where things are, back when there was no palette to apply. Every desktop screen they held now has a board, so they were removed rather than kept as a second drawing to update twice and disagree with once.

## The gate, in order

1. **Design the board in Penpot**, light and dark, at 1440×900, on the `Screens: <subject>` page for its product group — `Home`, `Workspace`, `Editor`, `Search`, and git split one page per feature (`Git - Commit`, `- Branches`, `- History`, `- Remote`, `- Diff`). A new group is a new page. **Split a page once it passes about four screens**: past that it scrolls beyond reading and stops working as a card.
2. **Build every control from the library.** A control that is not there yet becomes a master on `Components - Master`, with its variants, before the screen uses it.
3. **Export both boards** into `docs/design/screens/desktop/<page>/` and run `embed_fonts.py` over them.
4. **Link the screen** from the feature's `doc.md`, under `## Mocks`.
5. **Write the widget**, against what is on the board.
6. **Render it and compare.** The point of all of this is that the app looks like the design, and the only way to know is to look at both. Drive the screen in a test that captures a PNG at the board's own proportions, put it beside the export, and fix whichever one is wrong. A screen nobody compared is a screen that has already drifted.

A change to a shipped screen runs the same six steps. The board is edited, re-exported and committed *with* the code that changes — a board that no longer matches the app is worse than no board, because it carries the appearance of authority.

## Every control is a component

"Every button" is not a figure of speech. A control that appears on a screen exists as a **component master on the `Components - Master` page**, with its states as variants, and the screen places an instance of it. `Button` (Kind × Icon), `Chip`, `Field`, `Segmented · 2`, `Segmented · 3`, `Panel toggle`, `Theme toggle`, `Dot`, `Checkbox`, `Status mark`, `Select control`, `Notice band`, `Card` and `Popover` are already there.

Three pages divide the work and none of them do each other's: `Components - Master` holds the masters, `Components` the specimens one row per control, and `Foundations` the palette and the type scale with no component on it at all. Keeping them apart is what lets the library be read without the specimens in the way of it.

Two things follow from that, and both have bitten already:

- **A new control is a library change first.** Adding a master and its variants is a separate, smaller decision than the screen that needed it, and reviewing it separately is what keeps the set coherent.
- **An instance is never detached to restyle it.** If a screen needs a control to look different, the difference is a variant of the master, or the master is wrong.

Two Penpot facts the code has to encode: `library.components` lists one entry per variant *set*, and the rest are reached through `variants.variantComponents()`; and the plugin draws only on the **active page**, so anything touching the library switches page and switches back.

### Never move a master between pages

The masters live on `Components - Master`, in a board called `Masters`, and **they stay there**. Penpot keeps every component's original as a real shape, so the board cannot be deleted, and it cannot travel either:

- **Duplicating a page that holds main instances duplicates the components.** It did, twice, and both times it was the ten with variants.
- **Cut-and-paste does the same.** Penpot rebuilds a variant set that crosses a page.
- **The plugin cannot move a shape between pages at all** — `appendChild` answers `Cannot modify a page that is not currently active`, and a reference taken on one page is invalid on another.

What *is* safe to move is an ordinary instance, which is how the catalogue crossed pages without losing a component. **Before and after any page surgery, count the library**: a jump from 19 to 29 is the whole of the damage, and undo is the only clean repair.

### Making a component, and a variant set

`library.createComponent(shapes)` and `penpot.createVariantFromComponents(shapes)` both take **shapes**, never `LibraryComponent`. Passing components fails with `Code: :shapes`; pass each one's `mainInstance()` instead. The shapes must be on the active page.

A **slash in the name becomes a path**: creating `Panel toggle / Left Open` yields a component called `Left Open` under path `TOM / Panel toggle`. Name the parts plainly and let the variant set carry the family name. The grouped property arrives as `Property 1`, not as the word you had in mind, so read `variantProps` before writing code that switches on it.

**Grouping lowers the count**: four loose components become one set, so the library goes 24 → 21. That drop is the success signal, and the mirror image of the duplication failure above.

### A master carries no product words

A master's labels are `One`, `Two`, `Three`, never `Source`, `Split`, `Preview`. Text is a property, so the screen that places the instance writes the real words; a master that ships a product's vocabulary is a master that only fits one screen.

The same goes for the name: `Switch` is the on/off control, so a two-segment control is **not** a `Switch`. Where a family cannot be one variant set, put the distinction in the name — `Segmented · 2` and `Segmented · 3` — so the two sort together and neither collides with something else.

### A component must fit the use, not the other way round

`Segmented` ships three segments with fixed labels. The two-segment switches could not use it, because dropping a segment is a structural change to a copy, which Penpot forbids. They got `Switch two` instead. **When an existing component nearly fits, check whether the difference is a property (colour, size, text, flex) or a child — a property is an override and a child is a new component.**

### Never restructure a copy

`Cannot change the structure of a component copy` is Penpot refusing to add or remove a copy's children, and it is right to. So **editing a master means editing its children, never replacing them** — replace them and the copies keep the old structure and can no longer be repaired in place. When that has already happened, delete the stale instances and insert fresh ones of the right variant, then re-apply the theme colours, which are overrides and do survive.

Colour, size and flex *are* overridable on a copy. A control that looks wrong in one theme is usually an override that was never set, and a label sitting outside its control is usually a flex `justifyContent` with padding, not a bad `x`.

**A board carries no milestone chip.** `M0`, `M1`, `M2` are a wireframe's way of saying *this part arrives later*, and a board says what the app looks like — a chip on it is a note to the team pretending to be part of the product. The roadmap is where a milestone lives.

## Every page is a card

A page is one **card**: a board wide enough to hold the screens with the same frame every time, so nine pages read as one document rather than nine drawings.

| Element | Where |
|---|---|
| `title` | 64, 64 · 56pt, weight 600 |
| `note`, one sentence | 64, 148 · 28pt, regular |
| `shot title / <row>` | 64, row `y` − 48 · 26pt, weight 600 |
| dark board | 64, 286 |
| light board | 1552, 286 |
| `feat / <row> / …` | 3048, row `y` |
| next row | previous row `y` + board height + 136 |

The card is 3732 wide **only when the page has feature descriptions**; without them it ends where its content ends plus the same 64 it starts with. The light board carries the screens' own outer border, `#26251f` at 1pt.

**A label belongs above the board it names, not inside it.** And a board never repeats the card's title: the card is the frame and carries the words, the board is the content.

**Text boxes go stale.** A title that renders at half its size has a collapsed bounding box, not a wrong font — check `width`/`height` against a good card before touching the font. Resizing does not recompute it and neither does round-tripping `growType`; delete the text and create it again. A freshly created text measures `1x1` until the next call, so read it back in a separate one.

## Exporting

Every page produces two kinds of file, into `docs/design/screens/desktop/<page>/`:

| File | What it is | How |
|---|---|---|
| `<screen>-light.svg`, `<screen>-dark.svg` | the screen alone, both themes | `board.export({type: 'svg'})` then `embed_fonts.py` |
| `<page>.pdf` | the whole card: title, both themes, the notes beside them | `card.export({type: 'pdf'})` on the page's own card |

**SVG only for screens, never PNG.** The SVG keeps the text searchable and the diff readable, and once the fonts are in it is pixel-faithful. A PNG buys nothing and turns every review into a binary blob.

**`embed_fonts.py` is not optional.** Penpot's SVG export points its `@font-face` rules at Penpot's own font proxy, which nothing offline can reach, GitHub included. Without the script the text falls back to whatever font is at hand and every monospaced run reflows, which is a file that looks finished and is wrong.

```bash
python3 docs/design/tools/embed_fonts.py docs/design/screens/desktop/*/*.svg
```

**Do not judge the result with `rsvg-convert`.** It does not match a font family written `&quot;IBM Plex Mono&quot;` in an inline style against an `@font-face` that quotes it differently, so it drops every mono face and blames the file. Render with headless Chrome, which is what VS Code and GitHub use:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --force-device-scale-factor=2 --window-size=1444,1250 --screenshot=out.png "file://$PWD/<screen>.svg"
```

**An agent exports without reading a byte of it.** A board is 130–300KB of SVG and fifty will not fit through a conversation, so the plugin returns `{filename: base64}`, the harness writes that oversized answer to a file because it cannot be returned, and `tools/decode_exports.py` decodes it straight into place. The bytes go browser to disk and are never read. Return **only** the file map from the plugin: one stray diagnostic key and the decoder chokes on it. Do not try to post the bytes to a local server instead — the page is served over https, so the browser blocks it, and the sandbox blocks the server.

**Batch four to six boards per call.** Beyond that the plugin call passes 120 seconds and is moved to the background, where its answer is lost, and Penpot's own `/api/export` starts returning `:timeout`. A page of eight is two calls, split by theme.

The file name is the screen's name in kebab-case plus the theme: `branch-switcher-light.svg`. One screen is two files, always both.

## Look at it before committing

Render and actually view both themes. A board with a clipped label, a control that fell outside its panel or a dark variant nobody checked is invisible in an SVG diff and obvious on screen. The `export_shape` tool answers this directly.

**The card is not the screen.** Each page holds the screens inside a card that carries the title, the note and a column of what the screen is for. That framing is documentation and lives only in Penpot — an export is the board alone.

## Where the reasoning goes

Colour roles are decided in [visual-language](../../../docs/design/visual-language/README.md), the controls in [components](../../../docs/design/components/README.md), the identity in [brand](../../../docs/design/brand/README.md). None of it is annotated onto the board: a picture crowded with explanation stops being a design and starts being a diagram nobody updates.
